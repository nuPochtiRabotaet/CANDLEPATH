# Совместная разработка

1. Прочитать [индекс](README.md), [правила репозитория](../../AGENTS.md), текущий [аудит](BASELINE_AUDIT.md) и раздел своего этапа в [roadmap](ROADMAP.md). Индекс даёт цель; ветка, GitHub checks и код определяют фактическую реализацию.
2. Выполнить git fetch origin, проверить git status, HEAD базы, зависимости и открытые PR. Выбрать одну доступную задачу [backlog](IMPLEMENTATION_BACKLOG.md). Указать ID, владельца, второго reviewer, точный base SHA, ожидаемые файлы и приёмочные тесты в Issue или описании Draft PR. Для Project Board достаточно очереди Ready → In progress → Review → Done/Blocked с причиной блокировки.
3. От чистой origin/develop/v0.9 создать короткую ветку вида feat/base-01-paper-owner или docs/тема. Если необходим неслитый интерфейс, договориться о stacked PR к его head-ветке, указать SHA и порядок переноса. Не переносить пачку несвязанных исследовательских коммитов. Не перезаписывать чужую ветку или локальные правки.
4. Два разработчика заранее делят область записи. Например, один меняет контракт runtime, второй независимо готовит фикстуру отказа по согласованной версии схемы. При пересечении storage, risk, order state или migration сначала согласовать контракт и назначить одного автора интеграции. Автор и verifier указываются отдельно, бот не утверждает свой PR.
5. Сначала воспроизвести проблему на синтетических данных, затем изменить минимальный путь вызова и прогнать профильные регрессии. Для Paper использовать временный MOEX_DATA_DIR. Перед merge проверить полный Python-набор и затронутые JS/Chromium пути на точном SHA. Для docs проверить ссылки, JSON-примеры, Mermaid и согласованность терминов/ворот. В PR привести команду, окружение, exit code, число pass/fail/skip, ограничения и шаг отката.
6. PR содержит проблему, границы изменения, финансовые инварианты, совместимость существующих данных, результат теста до/после и ссылку на backlog. Для миграции приложить обратимый тест на копии и план восстановления, для изменения методов исследования — предрегистрацию нового эксперимента до исходов. Запрещено выдавать тест фикстуры или факт merge за разрешение включить исполнение.
7. Обновить соответствующую спецификацию и состояние ID. При пересмотре архитектуры добавить датированное решение в [журнал](README.md) с основаниями, альтернативой, рисками, владельцем и условием отмены. Предыдущее решение и отрицательные результаты сохранять. В контрольной точке интеграции фиксировать фактический SHA и свидетельства после принятия.

## Что требует согласования

Два разработчика совместно рассматривают границы инструментов агента, полномочия, сохранение/миграции, изменения Risk и Cost Engine, режимы исполнения, базы/валидацию стратегий, stop/TP/SL и доступ к секретам. Владелец отдельно утверждает риск-бюджет, внешнюю платформу, допустимые источники и активацию режима; требование независимых оценщиков для экономической и security-проверки сохраняется. Если автор одновременно представляет обе роли, привлечь независимого reviewer к соответствующему вороту.

Не выгружать пользовательские портфели, персональные Telegram-сообщения, API-ключи, сырые приватные fills или содержимое holdout в GitHub, CI-артефакты и промпты. Публиковать проверяемые агрегаты, хеши, команды и обезличенные синтетические примеры. Остановить затронутую часть задачи при неизвестном исходе заявки, доступе к чужой БД, спорных правах источника или невозможности проверить обязательный gate. Описать воспроизводимый блокер и продолжить независимые безопасные проверки.
